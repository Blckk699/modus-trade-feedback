## Общие правила

- Все маршруты под префиксом `/api/v1` (он уже входит в пути контракта; базовый адрес клиента — хост без префикса).
- Время — ISO 8601 со смещением. Часовой пояс системы UTC+5, сервер отдаёт время со смещением `+05:00`.
- Коды перечислений (статусы, типы, роли) — латиница; подписи на русском отдаёт `GET /dictionaries`.
- Клиент не дублирует правила прав и переходов: у обращения есть `allowed_actions`, у пользователя — `permissions`.
  Действие, которого нет в этих списках, клиент не показывает.
- Ошибка всегда в формате `Error`: `{\"error\": {\"code\": \"...\", \"message\": \"...\", \"details\": ...}}`.
  `message` можно показывать пользователю как есть, ветвиться — только по `code`.

## Авторизация

- Пользователь: `Authorization: Bearer <access_token>`. Токен выдают маршруты `/auth/_*`:
  почта и пароль (основной вход в вебе и мобильном приложении), Mini App, Telegram Login,
  одноразовый код из бота, dev-вход. Telegram — вход в один клик, привязывается к аккаунту (`/me/telegram`).
  Вход через Битрикс24 (`/auth/bitrix/_*`) — если включён на сервере (`GET /auth/methods`).
- Бот: `X-Service-Key: <ключ бота>` и `X-Telegram-Id: <Telegram ID пользователя>` — бот действует от имени
  пользователя, права проверяются так же, как для самого пользователя. Так бот вызывает любые
  пользовательские маршруты. Маршруты `/bot/_*` требуют только `X-Service-Key`.
- Незаведённый пользователь получает `403 user_not_registered`, отключённый — `403 user_disabled`.

Любой другой переход — `409 invalid_transition`. Отказ без причины, «В работу» без решения и
«Реализовано» без результата — `422 validation_error`.

**Кто выполняет действия.** Действия жизненного цикла выполняют ответственный обращения, руководитель
подразделения обращения и собственник. Руководитель и собственник действуют без смены ответственного:
для смены есть `reassign`. Администратор видит все обращения, но не меняет статусы, не склеивает,
не выносит на обсуждение, не создаёт задачи в Битрикс24 и не видит приватную переписку (`403`).
Автор пишет в переписку и отвечает на уточняющий вопрос.

**Срок.** В системе один срок — срок первого ответа. Он назначается при маршрутизации и при переназначении,
первый ответ фиксирует `take` (или `accept_feedback` у отзыва). Уточняющий вопрос задаётся уже после
первого ответа и на срок не влияет.
